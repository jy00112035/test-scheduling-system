## 一、需求背景

排班工作台中"按指定日期排班"和"按全部需求排班"两个功能在后端已经按优先级排序需求（高→中→低），但当人力不足时，低优先级需求出现缺口，用户无法看到：
1. 需求是按什么顺序被处理的
2. 为什么是这个需求缺人而不是别的需求
3. 哪些高优先级需求占用了关键资源

本次改造在排班前增加排序预览（可拖拽调整）+ 排班后增加资源竞争追溯。

## 三、新增 API

### `POST /api/schedules/recommend/preview`

**角色控制：** `resourceManager` / `projectManager` / `fieldAdmin`

**请求示例：**
```json
{
  "mode": "FULL_DEMAND",
  "demandIds": [1, 2, 3],
  "fixedStaffIds": [],
  "excludedStaffIds": [],
  "includeSaturdays": true,
  "includeSundays": true,
  "demandOfficePreferences": {},
  "demandOrder": [2, 1, 3]
}
```

**响应示例：**
```json
{
  "code": 200,
  "data": {
    "demandPreviews": [
      {
        "demandId": 2,
        "product": "产品B",
        "version": "v2.0",
        "priority": "高",
        "endDate": "2026-08-15",
        "totalManpower": 15.0,
        "estimatedAllocation": 12.0,
        "estimatedShortage": 3.0,
        "estimatedFulfilled": false,
        "competingDemands": [
          {
            "demandId": 1,
            "product": "产品A",
            "priority": "高",
            "testType": "功能测试",
            "contestedManpower": 5.0,
            "reason": "产品A(#1，高优先级)优先处理，占用了功能测试人员5.0人天"
          }
        ]
      }
    ],
    "globalWarnings": [
      {
        "testType": "功能测试",
        "totalRequired": 30.0,
        "totalAvailable": 20.0,
        "shortage": 10.0,
        "affectedDemandIds": [1, 2]
      }
    ],
    "sortOrder": [2, 1, 3],
    "totalStaffCapacity": 45.0,
    "totalDemandManpower": 50.0
  }
}
```

**算法说明：**
- 按 `demandOrder`（或默认 `demandComparator()`）排序需求
- 统计时间段内按测试类型的总人力容量：`Σ(人员系数 × 工作天数)`
- 按顺序依次"模拟扣除"各需求的人力
- 当某测试类型池耗尽时，后续依赖同类型的需求标记竞争关系
- 纯计算、不写库、`@Transactional(readOnly = true)`

### `POST /api/schedules/recommend/draft`（增强）

请求新增可选字段 `demandOrder: number[]`。传入后覆盖默认的 priority→endDate→createdAt 排序。Fulfillment 响应新增四个字段：

| 字段 | 类型 | 说明 |
|------|------|------|
| `processOrder` | int | 处理序号（1-based） |
| `totalDemands` | int | 本次排班需求总数 |
| `priority` | String | 需求优先级 |
| `contestedResources` | ContestedResource[] | 资源竞争明细 |

**ContestedResource 结构：**
```json
{
  "contestedByDemandId": 1,
  "contestedByProduct": "产品A",
  "contestedByPriority": "高",
  "contestedByOrder": 1,
  "testType": "功能测试",
  "contestedManpower": 5.0
}
```

## 五、关键技术细节

### 后端

1. **`demandOrderComparator()`** — 根据用户指定的 ID 顺序排序（位置越前排名越前），未出现在列表中的排最后
2. **`buildAllocatedByType()`** — 从 generated schedules 反推每个需求每个测试类型的分配量
3. **`computeContestedResources()`** — 对未满足的需求，遍历所有排在前面的需求，找出消费了相同测试类型的
4. **`preview()` 方法** — 轻量级，不获取悲观锁，不写库。使用 `default(LocalDate.now())` 处理 null 日期
5. **向后兼容** — `demandOrder` 可选，不传时使用现有 `demandComparator()` 排序

### 前端

1. **两步弹窗** — `recommendStep` 状态控制（1 或 2）。Step 2 的 footer 自定义布局（取消=上一步，确认=开始排班）
2. **@dnd-kit** — `DndContext` + `SortableContext` + `useSortable`。拖拽结束更新 `adjustedOrder` state
3. **预览加载** — Step 2 进入时用 `Spin` 包裹，调用 `previewScheduleDraft()` API
4. **竞争警告** — `DemandPreview.competingDemands` 数组驱动黄色警告条，实时随排序变化
