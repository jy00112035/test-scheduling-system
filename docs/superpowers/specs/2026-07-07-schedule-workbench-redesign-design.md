# 人力排布工作台重设计说明

## 背景

人力排布工作台面向资源主管和项目经理，用于对已经审批通过的测试需求进行人力排布。当前页面已经具备待排需求、人员日期矩阵、拖拽分配、推荐排班、冲突检测和发布能力，但当真实使用中待排需求和可分配人员数量增多时，用户会同时面对大量需求卡片、人员行、日期列和异常提示，操作路径容易变长。

本次设计选择“调度指挥台 + 两步式生成草稿”的方向：先按风险收束需求，再筛出匹配人员，随后生成可审查的推荐草稿，最后集中处理异常并发布。

## 设计目标

1. 降低资源主管在大量需求和大量人员中定位目标的成本。
2. 让用户先看到本批排布的可行性、缺口和冲突，再决定是否生成推荐草稿。
3. 保留人工微调能力，避免自动排布结果让用户失去控制感。
4. 把异常集中到一个明确区域，减少用户在全量矩阵里搜索冲突。
5. 延续 PRD 中“左侧待排需求 + 右侧排布视图”的核心模型，但将其升级为更适合批量操作的四区结构。

## 非目标

1. 不在本轮设计中重写后端排班算法。
2. 不改变测试需求审批流程。
3. 不改变人员系数、新员工递增、保密权限、测试类型等现有业务规则。
4. 不引入新的角色权限体系。

## 目标用户

### 资源主管

负责整体测试人力排布，需要快速知道哪些需求风险最高、哪些人员可用、哪些排布会产生冲突，并能批量发布排期。

### 项目经理

在资源不足或周期冲突时参与协调，需要清楚看到缺口原因，并判断是否调整测试周期或补充资源。

### 测试组长

在权限允许时查看本组人员可用状态和任务负载，辅助资源主管确认人力安排。

## 核心设计方向

采用四区布局：

1. 顶部调度总览条
2. 左侧需求队列
3. 中间匹配人员池
4. 右侧相关时间轴
5. 最右侧缺口与发布面板

页面默认不展示全量人员矩阵，而是先展示待处理需求。用户选择一批需求后，系统根据所选需求自动收束人员和日期范围，再在相关时间轴中展示排布结果。

## 信息架构

### 顶部调度总览条

顶部总览条始终固定在工作台顶部，展示当前排布上下文和主操作。

展示指标：

1. 待排需求数量
2. 高风险需求数量
3. 本批已选需求数量
4. 预计缺口人天
5. 草稿排班数量
6. 可发布需求数量

主操作：

1. `生成推荐草稿`
2. `只看异常`
3. `清除本批草稿`
4. `发布本批`

按钮状态规则：

1. 未选择需求时，`生成推荐草稿`禁用。
2. 选择需求后，先展示可行性预估，`生成推荐草稿`可用。
3. 草稿生成后，`发布本批`可用。
4. 存在冲突或缺口的需求默认不参与一键发布，除非用户单独处理完成。

### 左侧需求队列

需求队列负责帮助用户决定“先排哪些需求”。

默认排序：

1. 已超过或临近测试结束日期的需求
2. 剩余人天缺口大的需求
3. 优先级高的需求
4. 保密需求或特殊测试类型需求
5. 已有草稿但未发布的需求

筛选项：

1. 测试类型
2. 优先级
3. 产品
4. 版本类型
5. 截止时间
6. 是否保密
7. 是否已有草稿
8. 是否存在缺口

需求卡片展示：

1. 产品和版本
2. 优先级
3. 测试周期
4. 总人力需求
5. 已发布人天
6. 草稿人天
7. 剩余人天
8. 测试类型明细
9. 保密标识
10. 样机数量
11. 风险标签

交互规则：

1. 支持单选、批量勾选、全选当前筛选结果。
2. 点击需求卡片打开需求详情抽屉或弹窗。
3. 勾选需求后，匹配人员池和相关时间轴立即按本批需求刷新。
4. 对已经完全发布且未过期的需求，展示在“已分配”分组中，不进入默认待排队列。

### 中间匹配人员池

匹配人员池负责回答“哪些人适合当前这批需求”。

人员排序依据：

1. 测试类型匹配度
2. 熟悉模块匹配度
3. 保密权限匹配
4. 当前人力系数
5. 目标日期范围内可用率
6. 已有排班负载
7. 是否存在冲突

人员卡片展示：

1. 姓名
2. 测试类型
3. 当前系数
4. 熟悉模块
5. 保密权限
6. 本批日期范围内可用率
7. 当前冲突状态
8. 推荐匹配分

匹配分规则：

1. 测试类型完全匹配加权最高。
2. 熟悉模块命中需求产品或模块时加分。
3. 无保密权限的人员不能匹配保密需求。
4. 可用率低于本批最低投入要求时降分。
5. 已经超过容量的人员标记为冲突，不作为推荐首选。

交互规则：

1. 默认只展示与本批需求相关的人员。
2. 支持切换“全部人员”，用于手动兜底。
3. 点击人员卡片时，右侧时间轴聚焦该人员。
4. 可将人员固定到本批，生成草稿时优先尝试使用固定人员。
5. 可将人员排除出本批，生成草稿时不使用该人员。

### 右侧相关时间轴

相关时间轴负责展示本批需求与匹配人员在日期维度上的排布关系。

默认展示范围：

1. 如果已选择需求，展示本批需求的最早开始日期到最晚结束日期，默认最多展示两周。
2. 如果跨越超过两周，支持周切换和日期范围缩放。
3. 未选择需求时，展示本周和下周的容量概览。

时间轴行：

1. 匹配人员
2. 已固定人员
3. 存在冲突但与本批相关的人员
4. 缺口行

时间轴列：

1. 日期
2. 工作日和周末标识
3. 当日容量
4. 当日已占用比例

单元格展示：

1. 已发布排班
2. 草稿排班
3. 非空闲状态，例如请假、借调、其他任务
4. 总负载百分比
5. 冲突状态

交互规则：

1. 生成草稿前，时间轴展示容量、已有排班和可用空位。
2. 生成草稿后，时间轴展示推荐草稿，用户可以拖拽移动、修改百分比、删除草稿。
3. 已发布排班默认锁定，修改后进入本地待提交变更状态。
4. 冲突单元格高亮显示，并在缺口与发布面板同步列出原因。

### 缺口与发布面板

缺口与发布面板负责集中展示本批需求的可行性和异常。

生成草稿前展示：

1. 本批需求总人天
2. 预计可满足人天
3. 预计缺口人天
4. 缺口测试类型
5. 缺口原因
6. 建议动作

生成草稿后展示：

1. 已生成草稿数量
2. 无冲突可发布需求数量
3. 有冲突需求数量
4. 未满足需求数量
5. 每个异常需求的原因和建议动作

异常类型：

1. 单人单日负载超过当前容量
2. 新员工系数不足
3. 保密需求缺少可用保密人员
4. 指定测试类型没有可用人员
5. 样机数量限制导致无法并行分配
6. 需求周期过短导致人天无法满足
7. 已发布排班占用过高

建议动作：

1. 延长测试周期
2. 调整需求优先级
3. 排除冲突人员
4. 固定特定人员后重新生成
5. 触发项目经理协调
6. 保留为草稿暂不发布

发布规则：

1. 默认只发布无冲突且人力满足的需求。
2. 有缺口需求保留草稿，不进入一键发布。
3. 用户可以单独发布某个已满足需求。
4. 发布前二次确认，确认内容包含需求数量、排班条数、异常跳过数量。

## 核心流程

### 流程一：高风险需求优先排布

1. 用户进入人力排布工作台。
2. 左侧需求队列默认按风险排序。
3. 用户勾选一个或多个高风险需求。
4. 系统刷新顶部指标、匹配人员池、相关时间轴和缺口预估。
5. 用户查看是否有明显缺口。
6. 用户点击`生成推荐草稿`。
7. 系统生成本批草稿排班。
8. 用户在时间轴中微调草稿。
9. 用户在缺口与发布面板处理异常。
10. 用户发布本批中无冲突且已满足的需求。

### 流程二：按测试类型批量排布

1. 用户在需求队列选择测试类型筛选条件。
2. 系统只展示包含该测试类型人力需求的需求。
3. 用户全选当前筛选结果或手动勾选部分需求。
4. 匹配人员池优先展示该测试类型人员。
5. 用户生成推荐草稿。
6. 用户处理冲突并发布。

### 流程三：处理自动排布缺口

1. 系统生成草稿后发现部分需求未满足。
2. 缺口与发布面板展示缺口需求、缺口人天、缺口测试类型和原因。
3. 用户选择建议动作。
4. 如果选择延长周期，系统提示需要项目经理协调。
5. 如果选择固定人员，用户在人员池固定目标人员后重新生成草稿。
6. 如果选择保留草稿，系统允许发布其他无冲突需求。

## 状态模型

### 需求排布状态

1. `未选择`：需求在队列中，但不参与当前批次。
2. `本批已选`：需求参与当前批次，会影响匹配人员和缺口预估。
3. `预估有缺口`：尚未生成草稿，但系统判断当前资源不足。
4. `草稿已生成`：已生成未发布排班。
5. `草稿有冲突`：草稿中存在负载或规则冲突。
6. `可发布`：草稿无冲突且人力满足。
7. `已发布`：排班已发布。

### 排班卡片状态

1. `已发布`：默认锁定，视觉上使用稳定色。
2. `草稿`：可拖拽、可编辑、可删除。
3. `待提交变更`：已发布排班被修改后产生的本地待提交状态。
4. `冲突`：超容量、权限不匹配或周期不合法。

### 人员状态

1. `推荐`：匹配分高且可用率足够。
2. `可用`：符合基础条件但不是最优。
3. `低可用`：可用率不足或系数较低。
4. `冲突`：当前周期内已经超过容量。
5. `不可用`：权限、测试类型或状态不满足本批需求。

## 数据与计算要求

### 风险排序计算

风险排序需要综合以下因素：

1. 剩余天数越少，风险越高。
2. 剩余人天越多，风险越高。
3. 优先级越高，风险越高。
4. 保密需求没有足够保密人员时，风险升高。
5. 特定测试类型没有可用人员时，风险升高。
6. 已有草稿未发布时，单独标记但不一定提高风险。

### 人员匹配计算

匹配分可以先在前端派生，不要求后端新增接口。

基础分维度：

1. 测试类型匹配：0 到 40 分。
2. 熟悉模块匹配：0 到 20 分。
3. 可用容量：0 到 20 分。
4. 保密权限：0 或 10 分。
5. 当前冲突惩罚：0 到 -30 分。
6. 新员工系数惩罚：0 到 -10 分。

低于 40 分的人员默认不进入推荐人员池，但可通过“显示全部人员”查看。

### 缺口计算

缺口按测试类型分别计算，再汇总到需求。

计算口径：

1. 需求总人天来自测试需求的人力需求明细。
2. 已发布排班计入已满足人天。
3. 当前草稿计入草稿人天。
4. 人员单日容量受当前系数和每日可用状态影响。
5. 保密需求只统计有保密权限的人员容量。
6. 样机数量限制会限制同一需求同一天可并行安排的人数。

## 组件拆分建议

当前 `src/pages/ScheduleWorkbench.tsx` 文件职责过重。实施时建议在不改变功能边界的前提下拆分为以下组件和工具：

1. `ScheduleWorkbench.tsx`：页面容器，负责数据加载、主状态组合和 API 调用。
2. `workbench/WorkbenchSummaryBar.tsx`：顶部调度总览条。
3. `workbench/DemandQueue.tsx`：需求队列、筛选、排序、批量选择。
4. `workbench/StaffMatchPool.tsx`：匹配人员池、固定人员、排除人员。
5. `workbench/ScheduleTimeline.tsx`：相关时间轴、拖拽、编辑、删除。
6. `workbench/IssuePublishPanel.tsx`：缺口、冲突、建议动作和发布入口。
7. `workbench/workbenchCalculations.ts`：风险排序、匹配分、缺口计算、批次指标。
8. `workbench/workbenchTypes.ts`：批次状态、匹配结果、缺口明细等类型。

## 视觉原则

1. 页面应更像运营调度台，而不是普通卡片列表。
2. 使用紧凑但清晰的信息密度，避免大面积装饰。
3. 顶部指标和主操作固定，减少滚动后丢失上下文。
4. 风险和冲突使用稳定的红、橙色提示。
5. 草稿、已发布、待提交变更必须视觉区分。
6. 四区布局在宽屏下横向展开，在窄屏下允许分段折叠。

## 验收标准

1. 用户进入页面后能直接看到待排需求、高风险需求和草稿数量。
2. 用户可以按高风险排序快速选择一批需求。
3. 选择需求后，人员池只展示相关人员，并显示匹配原因和可用率。
4. 选择需求后，时间轴只展示本批相关人员和日期范围。
5. 生成推荐草稿前，用户能看到预计缺口和主要原因。
6. 生成推荐草稿后，草稿排班可编辑、可拖拽、可删除。
7. 冲突和缺口集中显示在缺口与发布面板。
8. 一键发布默认跳过有冲突或未满足的需求。
9. 已发布排班修改后进入待提交变更状态。
10. 现有 PRD 中的人力百分比分配、新员工系数、保密权限、冲突检测规则继续有效。

## 待用户确认的问题

1. 缺口需求是否允许强制发布。
2. “项目经理协调”是否需要在本次重设计中做成可点击流程入口。
3. 人员熟悉模块是否足够可靠，可以作为匹配分的重要依据。
4. 样机数量限制是否必须在首版重设计中参与自动推荐。

## 设计结论

本次重设计应采用“高风险优先 + 批量需求选择 + 匹配人员池 + 两步式生成草稿 + 异常集中发布”的工作流。它能把大规模排班从“在全量矩阵里找位置”转成“围绕一批需求进行调度”，更符合真实排班中的批量处理和异常优先处理方式。
