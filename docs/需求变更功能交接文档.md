## 一、功能概述

测试需求变更功能允许 `testManager` 对已审批通过的需求（`pending` 或 `scheduled` 状态）修改测试周期和人力配额，修改后需重新走审批流程。

### 状态流转图

```
submitted ──审批通过──→ pending ──提交变更──→ revision_pending
    ↑                      ↑                      │
    │                      │                      ├──批准──→ pending（无排班）/ scheduled（有排班）
    │                      │                      ├──退回──→ rejected
    │                      │                      └──修改后批准──→ pending / scheduled
    │                      │
    │              排班发布──┘
    │                      │
    └──重新提交── rejected ←┘
                        ↑
                        └──变更退回── revision_pending
```

### 核心业务规则

1. **只有 `testManager` 角色可以提交变更**
2. **只有 `projectManager`、`fieldAdmin`、`resourceManager` 可以审批变更**
3. **只能对 `pending` 或 `scheduled` 状态的需求提交变更**
4. **新人力配额 ≥ 已使用人力（过去排班）**
5. **缩短周期时，周期外的未来排班自动删除**
6. **减少配额时，超额的未来排班自动删除（按日期从后往前）**

## 二、API 接口清单

### 变更提交（testManager）

| 方法 | 路径 | 说明 |
|------|------|------|
| `PUT` | `/api/demands/{id}/revision` | 提交变更请求 |
| `GET` | `/api/demands/{id}/revision-diff` | 获取变更差异详情 |

**请求体 `RevisionRequest`：**
```json
{
  "startDate": "2026-08-05T00:00:00",
  "endDate": "2026-08-25T00:00:00",
  "manpowerDetails": [
    {"testType": "功能测试", "manpowerDemand": 8, "remark": ""},
    {"testType": "自动化测试", "manpowerDemand": 3, "remark": ""}
  ]
}
```

### 变更审批（projectManager / fieldAdmin / resourceManager）

| 方法 | 路径 | 说明 |
|------|------|------|
| `GET` | `/api/demands/revision-pending-approval` | 变更待审批列表 |
| `PUT` | `/api/demands/{id}/approve-revision` | 批准变更 |
| `PUT` | `/api/demands/{id}/reject-revision` | 退回变更 |
| `PUT` | `/api/demands/{id}/approve-revision-with-changes` | 修改后批准 |

**修改后批准请求体：**
```json
{
  "manpowerDetails": [
    {"testType": "功能测试", "manpowerDemand": 10, "remark": ""},
    {"testType": "自动化测试", "manpowerDemand": 5, "remark": ""}
  ]
}
```

## 四、本次修复的 Bug（2026-07-24）

### Bug 1：权限拒绝返回 HTTP 400 而非 403

- **文件**: `GlobalExceptionHandler.java`
- **原因**: `BusinessException` 统一被 `@ResponseStatus(HttpStatus.BAD_REQUEST)` 捕获
- **修复**: 对 `errorCode == "FORBIDDEN"` 的异常返回 `ResponseEntity.status(HttpStatus.FORBIDDEN)`

### Bug 2：`revision-diff` 的 `changes` 字段始终为空

- **文件**: `TestDemandService.java`
- **原因**: `getRevisionDiff()` 只设置了 `modified` 快照，没有原始快照可供对比
- **修复**:
  - `submitRevision()` 中在修改前保存原始快照到 `demand.revisionOriginalSnapshot`
  - `getRevisionDiff()` 中从存储的 JSON 反序列化原始快照，计算字段差异
  - 新增 `computeChanges()` 方法比较日期、总人力、各测试类型配额

### Bug 3：`revision-diff` 的 `deletedSchedules` 始终为空

- **文件**: `TestDemandService.java`
- **原因**: 删除的排班信息没有被持久化
- **修复**:
  - `submitRevision()` 中将删除的排班信息序列化到 `demand.revisionDeletedSchedules`
  - `getRevisionDiff()` 中反序列化并查询人员名称填充到响应中
  - 新增 `serializeDeletedSchedules()` 和 `deserializeDeletedSchedules()` 方法

### Bug 4：`completed` 状态缺少显式变更保护

- **文件**: `TestDemandService.java`
- **原因**: 只检查 `pending`/`scheduled`，`completed` 被隐式拒绝但错误信息不明确
- **修复**: 在 `submitRevision()` 中增加对 `completed` 和 `revision_pending` 的显式检查，返回明确错误信息

### 新增文件

- `V5__revision_snapshot.sql` — Flyway 迁移脚本，为 `test_demand` 表添加 `revision_original_snapshot` 和 `revision_deleted_schedules` 两列

## 七、已知限制和待改进

1. **变更差异对比仅保存修改前快照**：当前实现将原始快照 JSON 存储在 `test_demand` 表中，如果后续需求被多次变更，每次会覆盖前一次的快照。如需变更历史追溯，需要单独的变更记录表。

2. **`approveRevisionWithChanges` 缺少差异保存**：修改后批准时不会更新 `revisionOriginalSnapshot`，因为该操作直接完成审批，不再需要差异展示。

3. **人员名称查询**：`deserializeDeletedSchedules()` 通过 `testStaffRepository` 查询人员名称，如果人员被删除会显示"未知"。

4. **前端变更详情弹窗**：`RevisionApproval.tsx` 中的变更详情弹窗已适配后端返回的 `changes` 字段，但 `original` 快照的展示未做（当前只展示 `modified` 和 `changes`）。
