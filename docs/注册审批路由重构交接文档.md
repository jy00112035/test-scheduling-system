# 注册审批路由重构 — 交接文档

> 日期：2026-07-15

## 一、变更背景

原有审批路由存在以下问题：
1. 项目经理可审批字段管理员和项目经理的注册，但业务要求只有 admin 可以审批这两类角色
2. 资源经理没有注册审批权限，但业务要求资源经理可以审批所有测试员（不过滤 testType）
3. admin 账号没有独立的 `admin` 角色，只有 `fieldAdmin` + `testManager`

## 二、审批规则（变更后）

| 注册角色 | 审批人 | 备注 |
|---|---|---|
| 测试执行人员 (testExecutor) | 同 testType 的测试组长 **或** 资源经理 | 两者都能看到、都能审批；资源经理不过滤 testType |
| 测试经理 (testManager) | 项目经理 | |
| 资源经理 (resourceManager) | 项目经理 | |
| 测试组长 (testLead) | 项目经理 | |
| 字段管理员 (fieldAdmin) | admin | 仅 admin 可审批 |
| 项目经理 (projectManager) | admin | 仅 admin 可审批 |

**审批规则优先级（后端逻辑）：**
1. admin → 看到 fieldAdmin、projectManager 的待审批
2. projectManager → 看到 testManager、resourceManager、testLead 的待审批
3. resourceManager + testLead（双角色）→ 合并两者的范围
4. resourceManager → 看到所有 testExecutor（不过滤 testType）
5. testLead → 看到同 testType 的 testExecutor

### 4.2 admin 角色迁移（DataInitializer.java）

```java
private void migrateAdminRole() {
    userRepository.findByUsername("admin").ifPresent(admin -> {
        if (!admin.getRoles().contains("admin")) {
            List<String> roles = new java.util.ArrayList<>(admin.getRoles());
            roles.add(0, "admin");
            admin.setRoles(roles);
            userRepository.save(admin);
        }
    });
}
```

此方法在每次启动时运行，确保旧数据库的 admin 账号也能获得 `admin` 角色。幂等操作，重复执行无副作用。

## 六、已知限制

1. **SecurityConfig 无服务端权限校验**：所有端点仍是 `permitAll()`，审批权限完全依赖前端 UI 隐藏 + 后端按角色过滤返回数据。恶意用户可调用审批接口，但只能操作自己权限范围内的数据。
2. **admin 不可自注册**：`admin` 是系统管理角色，注册页面不提供此选项，仅通过 DataInitializer 初始化。
3. **拒绝操作为硬删除**：拒绝注册申请会直接删除用户记录，不可恢复。
