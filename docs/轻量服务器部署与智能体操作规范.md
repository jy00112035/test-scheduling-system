# 测试排班系统轻量服务器部署与智能体操作规范

**适用版本：** 包含“特殊模块人力需求与排班硬匹配”的版本及以后版本  
**目标：** 将系统稳定部署在一台轻量 Linux 服务器上，并避免“代码已更新、实际服务仍运行旧目录/旧分支”的问题。  
**适用对象：** 负责发布的运维人员、CI/CD 流程，以及可执行命令的部署智能体。

---

## 1. 核心原则

### 1.1 发布对象是“提交版本”，不是某个工作目录

每次发布必须指定一个 Git 提交 SHA（例如 `7ddce1f...`），并在发布记录中保存：

| 项目 | 必须记录的内容 |
| --- | --- |
| 代码版本 | 完整 Git commit SHA |
| 发布分支 | 已合并的发布分支，例如 `main` 或 `release/*` |
| 前端产物 | `dist/` 的构建时间和 SHA |
| 后端产物 | JAR 文件名、SHA-256、构建时间 |
| 数据库迁移 | Flyway 当前版本 |
| 发布人/智能体 | 操作者标识和执行时间 |

禁止以“当前目录看起来有新代码”“某个 worktree 里有新代码”作为发布依据。功能分支必须先推送到远程仓库并合并到约定的发布分支；服务器只从远程仓库的明确提交构建。

### 1.2 一台服务器只允许一个生产运行目录

生产服务的 `WorkingDirectory` 必须固定为：

```text
/srv/test-scheduling/current/backend
```

其中 `current` 是指向某个不可再修改发布目录的软链接，例如：

```text
/srv/test-scheduling/current -> /srv/test-scheduling/releases/20260723-7ddce1f
```

禁止 systemd、Nginx、Supervisor、Docker Compose 或手工后台命令指向：

- 用户 Home 目录下的临时 clone；
- Git worktree 目录；
- `/tmp`、桌面目录或编辑器缓存目录；
- 同时存在多个不清晰来源的 `npm run dev`、`mvn spring-boot:run` 进程。

### 1.3 生产环境只运行构建产物

| 组件 | 开发方式 | 生产方式 |
| --- | --- | --- |
| 前端 | `npm run dev`（Vite） | Nginx 托管 `dist/` 静态文件 |
| 后端 | `mvn spring-boot:run` | systemd 运行固定版本 JAR |
| 数据库 | H2 文件库可用于本地开发 | MySQL 8，开启 Flyway 迁移 |

Vite 开发服务器不属于生产部署方案。它会直接读取当前源代码目录，最容易出现“终端启动的位置不是最新功能所在位置”的问题。

### 1.4 数据与密钥独立于代码发布目录

- MySQL 数据库运行在独立服务或托管数据库中，不在发布目录内。
- `JWT_SECRET` 存在 `/etc/test-scheduling/backend.env`，不提交到 Git，也不随发布随机改变。
- 修改 `JWT_SECRET` 会使全部已登录用户的令牌失效；这属于计划内安全操作，不能在普通发布中无意发生。
- 禁止将生产密码、数据库 URL、JWT 密钥写入 Git、构建日志、部署报告或智能体对话记录。

## 2. 推荐架构

```text
浏览器
  |
  | HTTPS :443
  v
Nginx
  |-- /        -> /srv/test-scheduling/current/frontend/dist
  |-- /api/    -> 127.0.0.1:8080
  v
Spring Boot (systemd: test-scheduling-backend.service)
  |
  v
MySQL 8（本机或托管实例）
```

安全组/防火墙只需对公网开放：

- `22`：SSH，仅限运维来源 IP；
- `80`：HTTP，用于 HTTPS 跳转和证书校验；
- `443`：HTTPS；

不得对公网开放 `8080`、`3306`、H2 Console。后端仅监听 `127.0.0.1:8080`，由 Nginx 反向代理。

## 3. 服务器基线

以下以 Ubuntu 22.04/24.04 为例。建议轻量服务器最低配置为 2 vCPU、4 GB 内存、40 GB SSD；若 MySQL 与应用同机运行，建议 4 GB 内存起步并配置交换空间。

### 3.1 必备软件

| 软件 | 建议版本 | 用途 |
| --- | --- | --- |
| OpenJDK | 21 | 运行 Spring Boot 后端 |
| Node.js | 20 LTS | 构建 React 前端 |
| Maven | 3.9+ | 构建后端 JAR |
| Nginx | 当前稳定版 | HTTPS、静态文件与 API 代理 |
| MySQL | 8.0 | 生产数据库 |
| Git | 2.3+ | 获取指定提交 |

创建专用系统用户和目录：

```bash
sudo useradd --system --home /srv/test-scheduling --shell /usr/sbin/nologin test-scheduling
sudo install -d -o test-scheduling -g test-scheduling /srv/test-scheduling/releases
sudo install -d -o test-scheduling -g test-scheduling /srv/test-scheduling/shared
sudo install -d -o test-scheduling -g test-scheduling /var/log/test-scheduling
sudo install -d -o root -g test-scheduling -m 0750 /etc/test-scheduling
```

`/srv/test-scheduling/releases` 只放版本化的不可变发布包。不要在此目录直接编辑代码。

### 3.2 代码访问方式

给部署服务器配置只读 Deploy Key 或只读机器人 Token。部署智能体只能从远程仓库拉取指定 SHA，不能依赖本地未提交改动。

建议在服务器预置裸仓库：

```bash
sudo -u test-scheduling git clone --bare git@github.com:OWNER/REPOSITORY.git /srv/test-scheduling/repository.git
```

后续发布通过 `git --git-dir=/srv/test-scheduling/repository.git fetch --prune origin` 获取远程提交。

## 4. MySQL 与数据库迁移

### 4.1 创建最小权限账号

以下 SQL 由数据库管理员执行。生产密码须由密码管理器生成，不要使用示例值。

```sql
CREATE DATABASE test_scheduling
  CHARACTER SET utf8mb4
  COLLATE utf8mb4_0900_ai_ci;

CREATE USER 'test_scheduling'@'127.0.0.1'
  IDENTIFIED BY '由密码管理器生成的高强度密码';

GRANT SELECT, INSERT, UPDATE, DELETE,
      CREATE, ALTER, DROP, INDEX, REFERENCES
ON test_scheduling.* TO 'test_scheduling'@'127.0.0.1';
FLUSH PRIVILEGES;
```

如果 MySQL 是托管实例，将 `'127.0.0.1'` 改为应用服务器的私网 IP 或指定网段，并仅允许私网访问。

### 4.2 生产环境变量文件

创建 `/etc/test-scheduling/backend.env`，权限必须为 `0640`，所有者为 `root:test-scheduling`：

```ini
SPRING_PROFILES_ACTIVE=mysql
MYSQL_URL=jdbc:mysql://127.0.0.1:3306/test_scheduling?useUnicode=true&characterEncoding=utf8&serverTimezone=Asia/Shanghai
MYSQL_USERNAME=test_scheduling
MYSQL_PASSWORD=替换为真实密码
JWT_SECRET=替换为至少32字符且长期稳定的随机密钥
```

执行：

```bash
sudo chown root:test-scheduling /etc/test-scheduling/backend.env
sudo chmod 0640 /etc/test-scheduling/backend.env
```

当前后端要求通过 `JWT_SECRET` 注入签名密钥，且长度不得小于 32 个字符。生产部署必须显式设置 `SPRING_PROFILES_ACTIVE=mysql`；未设置时默认会使用 H2 文件数据库，属于部署失败。

### 4.3 Flyway 规则

系统使用 Flyway 管理结构变更，迁移文件位于：

```text
backend/src/main/resources/db/migration/
```

当前生产发布至少应包含 `V1` 至 `V4` 的迁移。启动后必须检查日志中 Flyway 的迁移结果，并执行：

```sql
SELECT installed_rank, version, description, success
FROM flyway_schema_history
ORDER BY installed_rank;
```

要求：

- 每条记录 `success = 1`；
- 最新版本与本次发布所带迁移一致；
- 不允许手工修改 Flyway 已执行迁移文件；
- 不允许手工删除 `flyway_schema_history`；
- 数据库迁移失败时，必须停止发布，不得通过关闭 Flyway 或改回 `ddl-auto=update` 绕过问题。

首次从历史 H2 数据迁移到 MySQL，应按独立迁移项目处理：先备份、导出、校验行数和抽样业务数据，再切换；不要在生产窗口内临时编写数据转换脚本。

## 5. 构建与发布目录

### 5.1 发布包的目录结构

每一次发布创建新目录，目录名包含 UTC/北京时间与短 SHA：

```text
/srv/test-scheduling/
├── repository.git/                 # 裸仓库，只由发布流程更新
├── releases/
│   ├── 20260723-7ddce1f/
│   │   ├── frontend/dist/
│   │   ├── backend/target/test-scheduling-backend-1.0.0.jar
│   │   ├── RELEASE.json
│   │   └── source/                 # 可选：本次构建源码快照
│   └── ...
├── current -> releases/20260723-7ddce1f
├── previous -> releases/20260710-<sha>
└── shared/
    └── backups/
```

`RELEASE.json` 最少包含：

```json
{
  "commit": "完整的40位Git SHA",
  "branch": "main",
  "builtAt": "2026-07-23T12:00:00+08:00",
  "frontendSha256": "...",
  "backendSha256": "...",
  "databaseProfile": "mysql"
}
```

### 5.2 构建门禁

构建来自已获取的提交，而非发布目录的残留文件。建议在 CI 构建并上传产物；资源有限时可在服务器构建，但必须先做以下校验：

```bash
git --git-dir=/srv/test-scheduling/repository.git fetch --prune origin
git --git-dir=/srv/test-scheduling/repository.git cat-file -e <COMMIT_SHA>^{commit}
git --git-dir=/srv/test-scheduling/repository.git merge-base --is-ancestor <COMMIT_SHA> origin/main
```

第三条失败表示该提交尚未合并进发布分支，部署智能体必须停止并报告，不能将本地 worktree 或未推送的功能分支当作生产版本。

构建前必须通过：

```bash
cd <源码目录>
npm ci
npm run lint
npm run build

cd backend
mvn clean test
mvn clean package -DskipTests
```

`mvn clean test` 应在 `package` 之前完成；`-DskipTests` 仅用于避免已通过的测试重复执行，并不表示跳过测试门禁。

### 5.3 参考发布脚本

将下列脚本作为 `/usr/local/sbin/deploy-test-scheduling`，仅允许受控发布用户执行。脚本的关键是：新建版本目录、确认 SHA、构建成功后才切换 `current` 链接。

```bash
#!/usr/bin/env bash
set -Eeuo pipefail

SHA="${1:?用法: deploy-test-scheduling <40位提交SHA>}"
ROOT=/srv/test-scheduling
REPO="$ROOT/repository.git"
STAMP="$(date +%Y%m%d-%H%M%S)"
SHORT_SHA="${SHA:0:7}"
RELEASE="$ROOT/releases/${STAMP}-${SHORT_SHA}"
SOURCE="$RELEASE/source"

test "${#SHA}" -eq 40
git --git-dir="$REPO" fetch --prune origin
git --git-dir="$REPO" cat-file -e "$SHA^{commit}"
git --git-dir="$REPO" merge-base --is-ancestor "$SHA" origin/main

install -d -o test-scheduling -g test-scheduling "$SOURCE"
git clone --no-checkout "$REPO" "$SOURCE"
git -C "$SOURCE" checkout --detach "$SHA"
chown -R test-scheduling:test-scheduling "$RELEASE"

sudo -u test-scheduling bash -lc "
  set -Eeuo pipefail
  cd '$SOURCE'
  npm ci
  npm run lint
  npm run build
  mkdir -p '$RELEASE/frontend'
  cp -a dist '$RELEASE/frontend/dist'

  cd backend
  mvn clean test
  mvn clean package -DskipTests
  mkdir -p '$RELEASE/backend/target'
  cp target/test-scheduling-backend-1.0.0.jar '$RELEASE/backend/target/'
"

test -f "$RELEASE/frontend/dist/index.html"
test -f "$RELEASE/backend/target/test-scheduling-backend-1.0.0.jar"

FRONTEND_SHA="$(sha256sum "$RELEASE/frontend/dist/index.html" | awk '{print $1}')"
BACKEND_SHA="$(sha256sum "$RELEASE/backend/target/test-scheduling-backend-1.0.0.jar" | awk '{print $1}')"
cat > "$RELEASE/RELEASE.json" <<EOF
{"commit":"$SHA","branch":"main","builtAt":"$(date -Is)","frontendIndexSha256":"$FRONTEND_SHA","backendSha256":"$BACKEND_SHA","databaseProfile":"mysql"}
EOF
chown -R test-scheduling:test-scheduling "$RELEASE"

if [ -L "$ROOT/current" ]; then
  ln -sfn "$(readlink -f "$ROOT/current")" "$ROOT/previous"
fi
ln -sfn "$RELEASE" "$ROOT/current"
systemctl restart test-scheduling-backend.service
systemctl reload nginx
```

> 注意：该示例假设发布分支为 `origin/main`。若团队正式分支不同，只能统一修改为一个明确名称，不能让智能体猜测分支。

发布脚本首次投入使用前应由管理员在测试服务器完整演练。智能体不得自行提升 `sudo` 权限、安装不明依赖或修改安全组。

## 6. systemd 后端服务

创建 `/etc/systemd/system/test-scheduling-backend.service`：

```ini
[Unit]
Description=Test Scheduling System Backend
After=network-online.target mysql.service
Wants=network-online.target

[Service]
Type=simple
User=test-scheduling
Group=test-scheduling
WorkingDirectory=/srv/test-scheduling/current/backend
EnvironmentFile=/etc/test-scheduling/backend.env
ExecStart=/usr/bin/java -Xms256m -Xmx768m -jar /srv/test-scheduling/current/backend/target/test-scheduling-backend-1.0.0.jar --server.address=127.0.0.1
SuccessExitStatus=143
Restart=on-failure
RestartSec=5
TimeoutStopSec=30
NoNewPrivileges=true
PrivateTmp=true
ProtectSystem=full
ReadWritePaths=/var/log/test-scheduling
StandardOutput=journal
StandardError=journal

[Install]
WantedBy=multi-user.target
```

启用服务：

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now test-scheduling-backend.service
sudo systemctl status test-scheduling-backend.service --no-pager
```

故障排查只使用：

```bash
sudo journalctl -u test-scheduling-backend.service -n 200 --no-pager
sudo systemctl show test-scheduling-backend.service -p MainPID -p ExecStart -p WorkingDirectory
sudo readlink -f /srv/test-scheduling/current
```

禁止以 `pkill -f java`、`kill -9` 或按端口模糊匹配的方式清理服务。这些做法可能杀掉错误进程，并掩盖“运行目录不一致”的根因。

## 7. Nginx 前端与反向代理

创建 `/etc/nginx/sites-available/test-scheduling`：

```nginx
server {
    listen 80;
    server_name scheduling.example.com;

    # HTTPS 配置完成后保留此跳转；证书申请期间可临时保留 ACME 路径。
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl http2;
    server_name scheduling.example.com;

    ssl_certificate     /etc/letsencrypt/live/scheduling.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/scheduling.example.com/privkey.pem;

    root /srv/test-scheduling/current/frontend/dist;
    index index.html;

    location /api/ {
        proxy_pass http://127.0.0.1:8080;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 60s;
    }

    location / {
        try_files $uri $uri/ /index.html;
    }

    location ~* \.(js|css|png|jpg|jpeg|gif|svg|ico|woff2)$ {
        expires 7d;
        add_header Cache-Control "public";
        try_files $uri =404;
    }
}
```

启用并验证：

```bash
sudo ln -sfn /etc/nginx/sites-available/test-scheduling /etc/nginx/sites-enabled/test-scheduling
sudo nginx -t
sudo systemctl reload nginx
```

前端请求使用相对路径 `/api`，因此生产环境不需要暴露 `8080`，也不应在前端编译时写死 `localhost:8080`。

## 8. 部署智能体的强制流程

以下流程是智能体每次发布必须执行的检查表。任何一项不通过都应停止，不得“尝试修一下继续发布”。

### 8.1 开始前

1. 接收人工明确提供的 `COMMIT_SHA` 和目标环境（测试/生产）。
2. 从远程仓库 fetch 后确认 SHA 存在。
3. 确认 SHA 已被 `origin/main`（或约定发布分支）包含。
4. 读取当前 `/srv/test-scheduling/current/RELEASE.json`，记录旧版本作为回滚点。
5. 检查磁盘可用空间、MySQL 连通性、`JWT_SECRET` 和 MySQL 三项环境变量存在但不输出其值。
6. 若检测到手工启动的 `npm run dev`、`mvn spring-boot:run` 或非 systemd 管理的 Java 后端占用生产端口，停止发布并要求人工处理。

### 8.2 构建和切换

1. 在全新 release 目录检出指定 SHA。
2. 运行前端 lint/build 与后端测试/package。
3. 写入 `RELEASE.json`，校验 `dist/index.html` 和 JAR 均存在。
4. 先将当前目录写入 `previous`，再原子切换 `current` 软链接。
5. 仅通过 `systemctl restart test-scheduling-backend.service` 重启后端；只通过 `systemctl reload nginx` 更新前端静态目录。

### 8.3 切换后验收

必须在同一次发布中得到以下证据：

```bash
# 1. 服务确实在 current 目录对应的版本上运行
readlink -f /srv/test-scheduling/current
cat /srv/test-scheduling/current/RELEASE.json
systemctl is-active test-scheduling-backend.service

# 2. 后端本机健康检查（根据实际健康端点调整；没有端点时检查 API 登录响应）
curl -fsS http://127.0.0.1:8080/api/auth/login \
  -X POST -H 'Content-Type: application/json' \
  -d '{"username":"发布验收专用账号","password":"仅从受控密钥系统读取"}'

# 3. 公网入口和静态首页
curl -fsSI https://scheduling.example.com/
curl -fsSI https://scheduling.example.com/api/

# 4. 数据库迁移版本
mysql --protocol=TCP -h 127.0.0.1 -u test_scheduling -p \
  -e 'SELECT version, success FROM test_scheduling.flyway_schema_history ORDER BY installed_rank;'
```

注意：验收账号密码也属于敏感信息。智能体只能从已授权的密钥存储读取，命令输出与发布报告中只记录“认证成功/失败”，不得记录密码或 JWT。

对于本次特殊模块功能，额外验收：

1. 前端登录后进入“测试需求管理 > 提交需求”。
2. 页面存在“特殊模块人力需求”和“新增特殊模块需求”。
3. 字段配置中可读取特殊模块配置。
4. 人员管理中可维护人员熟悉模块。
5. 人力排布中，选择特殊模块需求时，未熟悉该模块的测试员不可被分配；推荐结果仅返回符合条件的人员。

### 8.4 发布完成标准

仅当以下全部成立时，智能体才能报告“发布成功”：

- `current/RELEASE.json` 的 commit 等于人工指定 SHA；
- systemd 后端为 `active`，且日志未出现 Flyway/JPA/JWT 配置错误；
- 前端域名返回 `200`，`/api` 由 Nginx 正确转发；
- Flyway 迁移记录全部成功；
- 核心业务冒烟测试通过；
- 发布报告不包含密钥、密码、令牌或个人数据。

## 9. 回滚流程

应用代码回滚不等同于数据库回滚。Flyway 迁移默认只前进，因此任何包含数据库结构变更的版本都要先制定兼容窗口和数据回退方案。

### 9.1 仅代码回滚

适用于新旧版本均兼容当前数据库结构的情况：

```bash
sudo ln -sfn "$(readlink -f /srv/test-scheduling/previous)" /srv/test-scheduling/current
sudo systemctl restart test-scheduling-backend.service
sudo systemctl reload nginx
sudo systemctl status test-scheduling-backend.service --no-pager
```

随后重新执行第 8.3 节的验收，并记录故障版本 SHA、回滚版本 SHA 和原因。

### 9.2 涉及数据库迁移的回滚

若新版本执行了破坏性迁移、写入了新格式数据或旧版本无法兼容新结构：

1. 立即停止写入流量或进入维护模式；
2. 使用发布前完成的 MySQL 备份恢复到指定时间点；
3. 将应用回滚到与该数据库版本兼容的 release；
4. 由人工确认数据完整性后再恢复流量。

智能体不得自动执行生产数据库恢复、删库、清空表或强制修复 Flyway 历史。此类操作必须由具备数据库权限的人工确认。

## 10. 日常巡检与故障定位

### 10.1 每日检查

```bash
systemctl is-active test-scheduling-backend.service
df -h /srv /var
sudo journalctl -u test-scheduling-backend.service --since '24 hours ago' --priority=err --no-pager
mysql -e 'SELECT version, success FROM test_scheduling.flyway_schema_history ORDER BY installed_rank DESC LIMIT 5;'
```

建议监控：进程存活、HTTP 5xx、Nginx 5xx、JVM 内存、MySQL 连接数、磁盘空间、数据库备份结果和 TLS 证书到期时间。

### 10.2 “页面没有新功能”排查顺序

遇到发布后页面与预期不一致时，按以下顺序检查，不要先改代码：

1. 读取 `current/RELEASE.json`，确认 SHA 是否就是目标版本。
2. 读取 `readlink -f /srv/test-scheduling/current`，确认链接是否指向该 release。
3. 检查 systemd `ExecStart` 是否仅指向 `/srv/test-scheduling/current/...jar`。
4. 确认 Nginx `root` 是否仅指向 `/srv/test-scheduling/current/frontend/dist`。
5. 检查浏览器是否命中旧静态缓存，强制刷新并查看资源文件名是否更新。
6. 检查登录令牌是否因 `JWT_SECRET` 变化而失效，必要时重新登录。
7. 检查 API 是否返回新字段，确认数据库 Flyway 版本。
8. 最后才检查业务代码本身是否遗漏合并或构建失败。

### 10.3 本次问题的直接教训

本地曾出现：功能已在独立 worktree 的分支中完成，但浏览器中的 Vite 和 Spring Boot 服务仍从主工作目录启动。结果是浏览器显示旧功能，且后端与功能代码不一致。

本规范通过以下约束消除此类问题：

- 不在生产运行 `npm run dev` 和 `mvn spring-boot:run`；
- 以 commit SHA 和 `RELEASE.json` 作为唯一版本证据；
- Nginx、systemd 均只引用 `current` 软链接；
- 每次发布在新 release 目录构建，成功后再切换软链接；
- 智能体必须检查运行目录、服务定义、前端静态根目录和数据库迁移版本。

## 11. 部署智能体的禁止事项

部署智能体必须遵守以下限制：

1. 不得在未经人工指定 SHA 的情况下发布“最新代码”。
2. 不得从未推送的本地分支、临时 worktree 或脏工作目录发布。
3. 不得修改生产 `JWT_SECRET`、MySQL 密码、安全组、DNS 或 TLS 配置，除非收到明确、单独的人工授权。
4. 不得使用 `pkill`、`kill -9`、`rm -rf`、`git reset --hard` 等破坏性命令作为常规修复手段。
5. 不得关闭 Flyway、改为 JPA 自动建表、绕过失败迁移。
6. 不得将 H2 文件库作为生产数据库，也不得暴露 H2 Console。
7. 不得在日志、提交、报告或聊天中输出数据库密码、JWT、登录密码或完整连接凭据。
8. 任何数据库恢复、数据删除、迁移修复、生产回滚都必须在执行前请求人工确认。

## 12. 上线交接模板

每次发布结束后，部署智能体应以如下内容交接，不应只说“已部署”：

```text
环境：生产 / 测试
目标提交：<完整 SHA>
当前发布目录：/srv/test-scheduling/releases/<时间>-<短 SHA>
前一版本：<完整 SHA 或无>
后端状态：active
前端入口：https://<域名>/
数据库：MySQL，Flyway 已到 <版本>
核心验收：登录 / 提交测试需求 / 特殊模块需求 / 人力排布 <通过或失败>
回滚目录：/srv/test-scheduling/previous
未决事项：<无，或具体事项>
```

只有该记录与 `RELEASE.json`、systemd 状态、Flyway 历史一致，才算一次可追溯的部署。
